# Almacenamiento general de archivos en Amazon S3

Toda la aplicación usa un único proveedor (`STORAGE_PROVIDER=local|s3`) mediante
`common.storage.StorageService`. No se elige por módulo ni por tipo de archivo.
S3 utiliza el SDK oficial de Java. Preparar
el bucket privado y la identidad IAM según el archivo
`docs/storage/ALMACENAMIENTO-S3.md` del repositorio `bemol-api`, que contiene
la política y los pasos de configuración. Usar buckets distintos por entorno.

## Bucket privado

La plantilla [deploy/aws/storage.yaml](../deploy/aws/storage.yaml)
prepara un bucket nuevo con SSE-S3, bloqueo de acceso público, ACL deshabilitadas y
rechazo de HTTP. Incluye una política IAM de objetos limitada al prefijo; asociarla
únicamente a la identidad de la API. La plantilla no crea usuarios ni credenciales.
También mantener el bloqueo de acceso público a nivel de cuenta.

La plantilla no se aplica automáticamente. Prevé un bucket nuevo sin versionado,
sin Object Lock y sin reglas de expiración. No reutilizar un bucket versionado o
bloqueado: la limpieza de la API no elimina versiones ni vence retenciones.
No hay antivirus; la validación de formato de la aplicación no detecta malware.

## Variables del entorno

Configurar en `/opt/bemol-infra/.env.staging` del VPS, conservando permisos `0600`
(la plantilla pública es `.env.staging.example`):

```dotenv
STORAGE_PROVIDER=s3
STORAGE_S3_BUCKET=NOMBRE_DEL_BUCKET
STORAGE_S3_PREFIX=bemol/
AWS_REGION=us-east-1
AWS_ACCESS_KEY_ID=REEMPLAZAR
AWS_SECRET_ACCESS_KEY=REEMPLAZAR
AWS_SESSION_TOKEN=
```

Usar la región real del bucket. Con credenciales temporales, completar también
`AWS_SESSION_TOKEN` y renovar el conjunto cuando expire. En un host AWS con rol
IAM disponible para el contenedor, dejar vacías las tres variables de credenciales.
En un VPS externo, usar una identidad exclusiva de la API con permisos sobre el
prefijo configurado. El contenedor no hereda `~/.aws` del host.

`compose.yaml` pasa explícitamente estas variables a `api`. Por defecto el
proveedor sigue siendo `local`; los entornos actuales pueden seguir arrancando
sin AWS. El volumen local se monta en `/app/storage`.
Ni la API ni Compose crean buckets o modifican políticas IAM.

## Migrar un destino existente

Cambiar proveedor, bucket o `STORAGE_S3_PREFIX` no migra archivos. Antes de aplicar
el cambio sobre datos existentes:

1. Inventariar objetos, claves relativas y destinos persistidos en el journal;
   pausar escrituras y trabajos de limpieza durante la migración.
2. Preservar copias recuperables y copiar los archivos al destino nuevo sin cambiar
   sus claves relativas. Verificar contenido y permisos antes de cambiar variables.
3. Resolver los trabajos pendientes y referencias del journal con un plan específico:
   sus destinos no se actualizan automáticamente. Las consultas de sólo lectura están
   en `docs/enrollment/SEGURIDAD-DOCUMENTAL.md` del repositorio `bemol-api`.
4. Validar carga, lectura y eliminación antes de reabrir escrituras. Conservar el
   origen durante la ventana de rollback; retirarlo sólo tras aceptación explícita.

No borrar el origen ni sustituirlo por un destino vacío. Cambiar variables no es
una autorización para migrar o eliminar datos.

## Validar y aplicar cuando se active

Con el bucket y los permisos ya autorizados y provisionados:

1. Configurar las variables en el archivo privado `.env.staging`.
2. Seleccionar una imagen API compatible con S3 y una versión UI conocida.
3. Ejecutar `scripts/deploy-staging.sh` desde `/opt/bemol-infra` por SSH y revisar
   el resultado, healthchecks y logs según [la guía de staging](STAGING.md).

Un simple `restart` no aplica variables nuevas. El deploy usa el entrypoint SSH
compartido; con tags `staging` también puede actualizar las imágenes.
No aplicar esta receta sobre adjuntos locales existentes sin un plan de migración
aprobado y respaldos recuperables.

La API verifica escritura, lectura y eliminación de un objeto temporal al arrancar.
Después, comprobar carga, descarga autorizada y eliminación con documentación de
prueba. No hay cambio automático a local si falla AWS.

Los backups de objetos y PostgreSQL tienen una conservación independiente:
eliminar un objeto activo no borra copias de seguridad anteriores. Conservarlas
según la política institucional y verificar su eliminación por separado.

La API rechaza el arranque si hay trabajos pendientes o referencias activas del
journal en otro destino. Los trabajos conservan el destino donde
se crearon; no se redirigen automáticamente al cambiar las variables.

Aplicar la plantilla AWS y desplegar la aplicación son operaciones separadas.
Esta guía no acredita recursos provisionados ni acceso a una cuenta o bucket real.
