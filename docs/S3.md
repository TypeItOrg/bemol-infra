# Almacenamiento de archivos compatible con S3

Toda la aplicación almacena archivos en un servicio compatible con S3 mediante
`common.storage.StorageService`. No se elige por módulo ni por tipo de archivo.
S3 utiliza el SDK oficial de Java. Preparar el bucket privado y las credenciales
de AWS o R2 según el archivo
`docs/storage/ALMACENAMIENTO-S3.md` del repositorio `bemol-api`, que contiene
la política AWS y los pasos de configuración de ambos servicios. Usar buckets
distintos por entorno.

## Bucket privado en AWS

La plantilla [deploy/aws/storage.yaml](../deploy/aws/storage.yaml)
prepara un bucket nuevo con SSE-S3, bloqueo de acceso público, ACL deshabilitadas y
rechazo de HTTP. Incluye una política IAM de objetos limitada al prefijo; asociarla
únicamente a la identidad de la API. La plantilla no crea usuarios ni credenciales.
También mantener el bloqueo de acceso público a nivel de cuenta.

La plantilla no se aplica automáticamente. Prevé un bucket nuevo sin versionado,
sin Object Lock y sin reglas de expiración. No reutilizar un bucket versionado o
bloqueado: la limpieza de la API no elimina versiones ni vence retenciones.
No hay antivirus; la validación de formato de la aplicación no detecta malware.

## Variables del entorno

Configurar en `/opt/bemol-infra/.env.staging` del VPS, conservando permisos `0600`
(la plantilla pública es `.env.staging.example`):

```dotenv
STORAGE_S3_BUCKET=NOMBRE_DEL_BUCKET
STORAGE_S3_PREFIX=bemol/
STORAGE_S3_ENDPOINT=
STORAGE_S3_REGION=us-east-1
STORAGE_S3_ACCESS_KEY_ID=REEMPLAZAR
STORAGE_S3_SECRET_ACCESS_KEY=REEMPLAZAR
STORAGE_S3_SESSION_TOKEN=
```

Usar la región real del bucket. Con credenciales temporales, completar también
`STORAGE_S3_SESSION_TOKEN` y renovar el conjunto cuando expire. Usar una identidad
exclusiva de la API con permisos sobre el prefijo configurado. Las claves de
acceso y secreta son obligatorias.

`compose.yaml` pasa explícitamente estas variables a `api`. Ni la API ni Compose crean buckets o modifican políticas IAM.

Las variables `STORAGE_S3_*` son comunes a cualquier servicio compatible; el SDK
de AWS queda como detalle interno. El token de sesión es opcional. Una
configuración de claves ausente o parcial falla al arrancar, sin recurrir a otras
credenciales. No se usa la cadena automática del SDK, perfiles ni roles de
instancia. La región se toma únicamente de `STORAGE_S3_REGION`, cuyo valor
predeterminado es `us-east-1`.

Antes de activar `s3`, completar las variables genéricas en el archivo privado
del entorno. Compose sólo pasa estas variables de almacenamiento al contenedor.

## Cloudflare R2

Crear un bucket privado en R2 y credenciales **Object Read & Write** limitadas a
ese bucket. No habilitar acceso público. En el mismo archivo privado del entorno:

```dotenv
STORAGE_S3_BUCKET=NOMBRE_DEL_BUCKET
STORAGE_S3_PREFIX=bemol/
STORAGE_S3_ENDPOINT=https://ACCOUNT_ID.r2.cloudflarestorage.com
STORAGE_S3_REGION=auto
STORAGE_S3_ACCESS_KEY_ID=ACCESS_KEY_ID_DE_R2
STORAGE_S3_SECRET_ACCESS_KEY=SECRET_ACCESS_KEY_DE_R2
STORAGE_S3_SESSION_TOKEN=
```

Copiar el endpoint S3 de Cloudflare sin incluir el bucket; los buckets con
jurisdicción usan su endpoint específico. No usar una URL `r2.dev`, un dominio
público ni el token Bearer de Cloudflare. No se necesitan recursos AWS ni Workers.
La plantilla `deploy/aws/storage.yaml` y sus políticas IAM no se aplican a R2.

La API reutiliza el cliente S3 y aplica direccionamiento por ruta y desactiva
`chunked encoding` cuando hay un endpoint explícito. Dejar `STORAGE_S3_ENDPOINT`
vacío conserva la configuración predeterminada de AWS. No configurar reglas de
expiración ni retenciones que impidan borrar documentos de la aplicación.

## Assets públicos para los emails

Mantener privado el bucket de `STORAGE_S3_*`. Crear un bucket independiente para
assets públicos y subir allí `bemol-ui/public/brand/logo-email.png` desde el panel
de Cloudflare. Conectar un dominio propio para el uso compartido/producción;
`r2.dev` queda reservado para desarrollo.

Configurar en el archivo privado del entorno:

```dotenv
BRAND_LOGO_URL=https://assets.example.com/logo-email.png
```

Es la URL completa de la imagen, pública y estable, sin credenciales, consulta ni
fragmento. No usar el endpoint S3 ni una URL prefirmada. Compose la pasa sólo a la
API; no hacen falta nuevas credenciales S3 porque la API sólo la incluye en los
emails, sin descargarla ni administrar el bucket público.

Vacío mantiene `/brand/logo-email.png` en el frontend. La configuración reemplaza
el logo de Bemol, no los logos propios de cada institución ni los enlaces de acceso.
No modificar las variables documentales para apuntar al bucket de assets. Aplicar
el cambio mediante el procedimiento de despliegue autorizado; esta guía no publica
assets ni habilita acceso público automáticamente.

## Migrar un destino existente

Cambiar proveedor, bucket, `STORAGE_S3_PREFIX` o `STORAGE_S3_ENDPOINT` no migra
archivos. Con endpoint explícito, la ubicación del journal incluye endpoint y
bucket para distinguir servicios y cuentas con buckets del mismo nombre; sin
endpoint, AWS conserva la ubicación histórica por nombre de bucket.
Antes de aplicar el cambio sobre datos existentes:

1. Inventariar objetos, claves relativas y destinos persistidos en el journal;
   pausar escrituras y trabajos de limpieza durante la migración.
2. Preservar copias recuperables y copiar los archivos al destino nuevo sin cambiar
   sus claves relativas. Verificar contenido y permisos antes de cambiar variables.
3. Resolver los trabajos pendientes y referencias del journal con un plan específico:
   sus destinos no se actualizan automáticamente. Las consultas de sólo lectura están
   en `docs/enrollment/SEGURIDAD-DOCUMENTAL.md` del repositorio `bemol-api`.
4. Validar carga, lectura y eliminación antes de reabrir escrituras. Conservar el
   origen durante la ventana de rollback; retirarlo sólo tras aceptación explícita.

No borrar el origen ni sustituirlo por un destino vacío. Cambiar variables no es
una autorización para migrar o eliminar datos.

## Validar y aplicar cuando se active

Con el bucket y los permisos ya autorizados y provisionados:

1. Configurar las variables en el archivo privado `.env.staging`.
2. Seleccionar una imagen API compatible con S3 y una versión UI conocida.
3. Ejecutar `scripts/deploy-staging.sh` desde `/opt/bemol-infra` por SSH y revisar
   el resultado, healthchecks y logs según [la guía de staging](STAGING.md).

Un simple `restart` no aplica variables nuevas. El deploy usa el entrypoint SSH
compartido; con tags `staging` también puede actualizar las imágenes.
No aplicar esta receta sobre adjuntos locales existentes sin un plan de migración
aprobado y respaldos recuperables.

La API verifica escritura, lectura y eliminación de un objeto temporal al arrancar.
Después, comprobar carga, descarga autorizada y eliminación con documentación de
prueba. No hay cambio automático a local si falla S3 o R2.

Los backups de objetos y PostgreSQL tienen una conservación independiente:
eliminar un objeto activo no borra copias de seguridad anteriores. Conservarlas
según la política institucional y verificar su eliminación por separado.

La API rechaza el arranque si hay trabajos pendientes o referencias activas del
journal en otro destino. Los trabajos conservan el destino donde
se crearon; no se redirigen automáticamente al cambiar las variables.

Aplicar la plantilla AWS y desplegar la aplicación son operaciones separadas.
Esta guía no acredita recursos provisionados ni acceso a una cuenta o bucket real.
La carga, descarga y limpieza contra un bucket R2 real están pendientes de validación.
